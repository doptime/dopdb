# dopdb stress report — Go vs TypeScript engine

**Date:** 2026-08-19 · **Run:** `bench/run.sh` matrices, 9 scenarios × concurrency {4, 16, 64}, 10s windows, HTTP keep-alive load client (`cmd/stress load`)

## Environment

| | |
|---|---|
| Machine | Apple M1 (8-core), macOS 15, laptop — **not** an isolated benchmark rig; treat numbers as directional |
| Store | KVRocks 2.16.0 (commit `28440b5`), built native arm64 from source, local (`127.0.0.1:6666`) |
| Go engine | `bin/stress serve` (Go 1.22, `cmd/stress/serve.go`), ns `stress_go`, :8091 |
| TS engine | `tsx ts/stress/server.ts` (Node 19), ns `stress_ts`, :8092 |
| Dataset | `notes`: 50 users × 50 docs = 2,500 CBOR docs in one Redis hash, owner-scoped (`owner` ← JWT `uid`). `kv`/`queue`/`tags`/`board` native-type collections, **unscoped** |

Engines were verified equivalent **before** benchmarking: `DOPDB_TEST_KVROCKS_URI=… go test -run Conformance ./httpserve/` — 22/22 green, including the new cross-tenant per-key case. The load harness measures performance only; equivalence is the conformance suite's job.

## Finding 1 — Go scoped per-key reads were O(collection) — **fixed, 13–28×**

**Before:** Go's owner-scoped `hget`/`hexists`/`hdel`/`hsetnx`/scoped `hmget` routed through `findDS` — a full-collection `HGETALL` + N CBOR decodes + in-process filter, per request. TS already did the O(1) thing (`b.get` + owner predicate). At 2,500 docs that is ~10–20ms of scan per read.

**Fix** (`http_accessor.go`): `scopedDoc(ctx, ds, key, scope)` — one `HGET`, one `decodeDoc`, one owner-field compare. Absent and foreign both read as `ok=false`; no caller can probe another tenant's ids. `putScoped`/`incrScoped` atomic paths untouched. Whole-collection ops (find/hgetall/count/hkeys) intentionally remain scans — documented architecture, identical on both engines.

| c | crud before | crud after | speedup | hget p50 before | after |
|---|---|---|---|---|---|
| 4 | 374 ops/s | 10,334 ops/s | **28×** | 11.4ms | **0.2ms** |
| 16 | 431 ops/s | 10,207 ops/s | **24×** | 39.6ms | 0.3ms |
| 64 | 435 ops/s | 5,658 ops/s | **13×** | 123ms | 0.4ms |

Behavior contract pinned by the new `TestConformanceCrossTenantPerKey` (both engines): foreign `hget` → 404, `hexists` → false, `hmget` → `[null,…]`, foreign/absent indistinguishable, owner's doc survives.

*Honest confound:* the pre-fix matrix's whole-collection reads (find c64 p50 154→495ms) drifted too — the post-fix run wrote 4.8M requests vs 2.8M, leaving RocksDB a compaction backlog and mutated data (crud overwrote the `tag` fields the find scenario filters on). The find code path is untouched; both engines drifted together, so the **cross-engine** find comparison stands, the before/after one does not.

## Finding 2 — WATCH contention is the tail everywhere a hash is hot

Scoped writes (`hset`, `hincrby`) run as WATCH/MULTI transactions. A Hash collection is **one Redis key**, so WATCH serializes at collection granularity: every scoped write to any of the 2,500 rows watches the same key. At c64:

| op | Go p50 | Go p99 | Go 500s | TS p50 | TS p99 | TS 500s |
|---|---|---|---|---|---|---|
| hset | 18.4ms | 406ms | 52 | 49.0ms | 132ms | 0 |
| hincrby | 14.2ms | 351ms | 26 | 16.3ms | 53ms | 0 |

- Go's `watchRetry` (`watchAttempts = 64`) exhausts under c64 contention → **500 "write contention"**. TS retries until it wins — zero errors, but pays in latency (hset p50 49ms).

## Finding 3 — ZSet hot-key: Go 2–4.8× slower, cause open

The zset scenario deliberately hammers **one shared key** (`f=board`) — unlike list/set/str which use per-user keys. At c4 (no contention), every Go z op has a ~2.1ms floor while Go's own str ops run at 0.17ms — a 12× family gap. TS shows no such gap (str 0.26ms, z 0.39ms); its z ops are 5× faster than Go's. The effect is uniform across reads and writes (zscore 2.1ms, zadd 2.3ms, zrange-50 4.5ms), so it is not response size, and `board` is unscoped — the owner claim/check are no-ops on the Go side. Exact attribution (Go dispatch layer vs go-redis vs hot-key serialization) is open — flagged as follow-up. At c64 both engines degrade (Go ~70ms, TS ~41ms p50) from the shared-key serialization.

## Finding 4 — cross-engine hdel divergence caught by the probe, aligned

A manual cross-tenant probe during this session found scoped `hdel` on a foreign key returned **403 on Go, `ok:true` on TS** — TS silently no-opped. Both are non-leaking (Go 403s foreign and absent alike), but AGENTS.md §8 documents 403 = "accessing another user's data". Fix: TS `hdel`/`del` now do the sequential per-key ownership check — first unowned key (foreign **or** absent) aborts with 403 after earlier keys were deleted, byte-for-byte Go's loop semantics. Pinned by `TestConformanceCrossTenantPerKey`, including the multi-key partial-delete shape. (hdel is not in any benchmark scenario, so the numbers above predate and are unaffected by this change.)

## Reproduce

```sh
# KVRocks up on :6666, Go toolchain, ts/node_modules installed
bench/run-all.sh                 # sequential: Go matrix, then TS matrix
python3 bench/report.py          # regenerate the tables
DOPDB_TEST_KVROCKS_URI=redis://127.0.0.1:6666 go test -count=1 -run Conformance ./httpserve/
```

KVRocks build from source (native arm64, no Rosetta): `git clone https://github.com/apache/kvrocks && cd kvrocks && ./x.py build -j8` → `build/kvrocks` (2.16.0). Config: `bind 127.0.0.1`, `port 6666`.
